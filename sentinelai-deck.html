02 / 11Problem Understanding & Solution20 marks

Scanners find issues. Nobody reads 200 of them.

Semgrep, Gitleaks, and OSV-Scanner are individually reliable — but raw output is noisy, disconnected, and blind to the bugs that live in business logic, not syntax.

Scanner noise

Real repos return dozens to hundreds of findings across three tools with no shared context — teams triage by severity label, not by what's actually exploitable.

Invisible business-logic bugs

A missing lock between a "check" and a "commit" — e.g. a coupon that should redeem once — has no signature any SAST rule matches. It's correct-looking code with a timing hole.

False-positive fatigue

When every flagged line looks equally urgent, the handful of genuinely chainable, exploitable issues get buried under ones that were never real.

Our solution

SentinelAI keeps the proven scanners for raw signal, then adds a reasoning layer that reads business intent, composes individually-boring findings into realistic multi-step attack chains, and verifies which chains actually work before reporting anything — so the deliverable is a short list of confirmed attack stories, each with a plain-English narrative and a suggested fix.

Aligned to domain

Cybersecurity — AppSec / DevSecOps tooling that plugs into how security teams already scan repos, rather than replacing their tools.

Real user need, practical & feasible

Built for security engineers and small teams without a dedicated red team. Runs on any local folder or public GitHub repo; zero required config beyond one free Groq API key.

03 / 11Innovation & Creativity15 marks

Verification is the differentiator

Most "AI security scanner" ideas stop at "an LLM read the code and says it's vulnerable." SentinelAI treats that as a hypothesis, not a verdict — and tries to prove or kill it.

🧪 Dynamic exploitation, not just narration

For race-condition chains, SentinelAI clones the target into a disposable sandbox, boots it on a free port, gets one real session token, then fires 200 concurrent requests reusing that session with a non-pooled HTTP client — so requests genuinely land concurrently instead of serializing through Node's keep-alive pool. More than one success proves the exploit.

🕵️ A skeptical fallback verifier

When dynamic execution isn't possible, a second, adversarial LLM pass re-reads the exact code and only confirms the chain if it can cite a specific missing lock or transaction — otherwise it kills the candidate as a false positive, instead of rubber-stamping the Planner's guess.

🔗 Cross-file mitigation awareness

The static re-verifier resolves a flagged file's own local imports (e.g. a route handler's data model) so a mitigation living in a different file — like a Mongoose unique: true constraint — isn't invisible to it. Verified in testing: this correctly demoted a "duplicate registration" chain once the model's constraint was visible.

🧠 Business intent as a first-class stage

A dedicated Business-Logic Agent reads the intended rule behind an endpoint ("a coupon should apply once per order") before the Planner is ever allowed to reason about how that rule could be broken — chains are grounded in intent, not pattern-matched.

Differentiation

Not a linter wrapper. Not a chatbot pasted over scan output. An agent pipeline where each stage's explicit job is to eliminate the false positives the previous stage couldn't.

05 / 11Technical Implementation25 marks

Reasoning that composes, verification that proves

Two LLM-backed stages, each with a narrow job — the Planner only composes what the Business-Logic Agent already grounded in intent; the Verifier only confirms what it can independently prove.

  BL --> N["Business-Logic Notes\nintended rule + concern"]
  F --> PL["Planner Agent"]
  N --> PL
  PL --> AC["Candidate Attack Chains\nnarrative + steps + impact + suggested fix"]
Verify stage
flowchart TD
  AC["Candidate attack chain"] --> T{"type: race-condition?"}
  T -- yes --> RS["LLM synthesizes a request spec\nendpoint, body, how to get a token"]
  RS --> BOOT{"bootable local server?"}
  BOOT -- yes --> SBX["Disposable sandbox\nnpm install, boot on a free port"]

  CNT -- no --> NO1["Not confirmed"]

  T -- no --> STA
  STA --> CITE{"cites a missing lock / transaction?"}
  CITE -- yes --> OK2["Verified"]
  CITE -- no --> NO2["Killed as false positive"]

06 / 11Technical Implementation25 marks

Engineering for real repos, not just the demo

Two things exist specifically so a scan on a real company repo can't silently fail or crash mid-run.

Per-request token budgeting

src/reason/findingsBudget.ts caps and prioritizes findings by severity, spread across tools, before they enter a prompt — instead of dumping the full findings list and risking a provider's token limit. Hit for real during development: a monorepo with 113 raw findings blew past Groq's on-demand tier limit and crashed the run before this existed.

Graceful degradation

src/pipeline.ts — if Reason or Verify errors out (rate limit, provider hiccup, network blip), the pipeline logs it and continues with what it has (Sense findings alone, or unconfirmed chains) rather than crashing with zero output. A partial report beats no report.

Schema-validated LLM output

Every structured LLM response (business-logic notes, attack chains, request specs) is parsed through a Zod schema before it touches the pipeline — a malformed model response fails loudly and locally instead of corrupting downstream stages.

Provider-agnostic reasoning layer

src/reason/llm.ts abstracts Groq-hosted Llama 3.3 70B (default, free tier) vs. fully local Ollama — a drop-in swap, no other code changes required. No OpenAI or Claude API dependency.

09 / 11Scalability & Real-World Impact10 marks

Beyond the fixture

Real-world applicability

Same command works against any public GitHub repo or local folder: npm run dev -- scan owner/repo — the bundled fixture demonstrates the loop, it isn't a hardcoded special case.

Scalability, proven not aspirational

Per-request token budgeting and graceful degradation were built because a real 113-finding monorepo scan hit a provider token limit during development — the fix is already shipped, not a roadmap item.

Business potential

Slots into DevSecOps triage as a noise-reduction + verification layer on top of scanners teams already run, rather than asking them to replace tooling. --publish can open a GitHub Issue and an auto-drafted fix PR for confirmed chains automatically.

Long-term impact

Hackathon scope proves one high-impact chain type (business-logic + token race conditions) end-to-end, deliberately over shallow coverage of many types — the harder, more valuable claim to prove first.

Roadmap

More chain types beyond business-logic races · CI/CD integration (run on every PR via the GitHub App webhook) · a team dashboard aggregating verified findings across repos.
